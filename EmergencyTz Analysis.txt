3. Architecture
---------------

Single-module (`:app`), single-screen, no clean-architecture layering at all.
Flat package layout:

```
tz.emergency.app
|-- EmergencyService.kt          domain model (enum, constants)
|-- MainActivity.kt              entry point + ALL business logic
+-- ui
    |-- EmergencyTanzaniaApp.kt  the only screen
    |-- services/                button components + icons
    +-- theme/Theme.kt
```

Characteristics:
- **UI-driven, no ViewModel.** No `androidx.lifecycle`, no `ViewModel`, no
  StateFlow, no coroutines. The screen is a pure stateless `@Composable`.
- **Logic lives in the Activity.** `MainActivity.kt:58-88` owns permission
  checks, number resolution, and the debug/release branching -- it never
  delegates to a repository or use-case layer.
- **No data layer at all.** No Room, no DataStore, no network, no
  serialization. The only persisted state is one boolean in `SharedPreferences`
  (`"emergency_tanzania"` -> `call_permission_requested`), used solely to avoid
  re-prompting.
- **Hardcoded data.** Numbers live directly in the enum
  (`EmergencyService.kt:15-17`) with no remote config or resource indirection.
- **Icons hand-built** as `ImageVector` path literals in
  `EmergencyServiceButton.kt:82-110` -- no Compose Material icon dependency, no
  SVG/vector drawable assets. `res/` contains no drawables or strings at all.

6. Permissions
--------------

Manifest declares exactly one permission:

```xml
<uses-permission android:name="android.permission.CALL_PHONE" />
```

This is the **dangerous** `CALL_PHONE`, not `ACTION_DIAL` -- meaning the app
places calls with **no user confirmation dialog**. For an emergency app this is
arguably the right call, but it's a deliberate trade-off worth being aware of.

`allowBackup="false"`, `supportsRtl="true"`, single exported launcher activity.


7. The Debug/Release Safety Mechanism
-------------------------------------

This is the most interesting engineering decision in the codebase, at
`app/build.gradle.kts:4-12, 43-51`:

1. `local.properties` is read at configure time and `DEBUG_TEST_PHONE_NUMBER` is
   injected as a `buildConfigField`.
2. The `release` build type is **not** configured, so it inherits the
   `defaultConfig` field, hardcoded to `""` (`app/build.gradle.kts:30`).
3. `MainActivity.kt:76-88` -- `numberToCall()`: if `!BuildConfig.DEBUG` -> real
   number. If debug and the test number is empty -> **refuse to dial**, show a
   toast, return `null`.
4. `MainActivity.kt:39-41` -- the same guard gates the "TEST MODE" banner in the
   UI.

Net effect: **a debug APK physically cannot dial 112/114/115**, even if
`local.properties` is missing or empty. That's a solid safety design for a repo
that will be handed around as a zip. The escaping logic
(`replace("\\","\\\\")`) prevents a stray quote or backslash in the number from
breaking the generated Java.
